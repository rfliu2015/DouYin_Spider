### 2.2 `public-key`

**文章说**：

> 可忽略：最后发现浏览器里会存到 localStorage 里面
> 传入一个 e, r 这是一个私钥一个公钥
> 大概意思是浏览器会一开始生成一个 ECDH 密钥，后面的计算都用到了这个东西，**把它看成浏览器环境对应账号就好了**
> 一个账号/一个环境对应一个公钥私钥就好了，所以把 e, r 都复制下来先

**这是全文对我们最有价值的一句话。**

它印证了 [03-扫码登录攻坚.md](03-扫码登录攻坚.md) 里的核心判断：

> **私钥不是服务端给的，是本地生成的。一个账号/一个环境对应一个公钥私钥。**

项目侧对应实现（`utils/passport.py:55`）：

```python
def generate_ec_keypair():
    """生成 bd-ticket-guard 用的 P-256 密钥对（PEM）。"""
    sk = SigningKey.generate(curve=NIST256p)
    return sk.to_pem().decode(), sk.get_verifying_key().to_pem().decode()
```

**但这里有个重要差异**：

| 维度 | 文章做法 | 项目做法 |
|---|---|---|
| 密钥来源 | 从浏览器 localStorage **复制**现成的 | **自己生成**新的 P-256 |
| 适用场景 | 接管一个已登录的浏览器环境 | 从零走一遍登录 |

**这正是我们扫码失败的结构性矛盾的根源**：项目每次登录都生成新密钥，无法复用浏览器里那把已经被服务端信任的密钥。

**文章提示了一条我们没试过的路**：既然密钥可以「复制下来」，那理论上可以从 dyclaw 的浏览器 profile 里把 `e` / `r` 导出来，让项目用这把**已经被服务端信任的密钥**，而不是自己生成新的。

### 2.3 `bd-ticket-guard-client-data`

**文章说**：

> 多次看 headers 的 client_data 参数，base64 解一下，发现只有 `req_sign` 和 `datestamp` 会变，所以要搞定这两个东西（其他的 `ts_sign` 等信息登录之后就能拿到 所以忽略）
> 首先要先跟一下这个 `ecdh_key`（私钥和证书生成的）
> 然后组装一下 base64 就得到结果了

**项目实现**（`utils/bd_ticket.py`）：

```python
def derive_ecdh_key(prv: str, server_cert: str) -> bytes:
    """ECDH(客户端私钥, 服务端证书公钥) -> HKDF-SHA256 -> 32 字节 HMAC 密钥。"""
    ...
    return _hkdf_sha256(shared)

def get_req_sign_hmac(e, ecdh_key: bytes) -> str:
    return base64.b64encode(
        hmac.new(ecdh_key, e.encode("utf-8"), hashlib.sha256).digest()
    )

def generate_bd_ticket_client_data(api, ticket, ts_sign, prv, ecdh_key=None,
                                   timestamp=None, t_trust=None):
    """:return: (client_data_b64, algo_type)"""
    timestamp = int(time.time()) if timestamp is None else int(timestamp)
    res_sign = f"ticket={ticket}&path={api}&timestamp={timestamp}"
    if ecdh_key:
        req_sign, algo_type = get_req_sign_hmac(res_sign, ecdh_key), "hmac"
    else:
        req_sign, algo_type = get_req_sign(res_sign, prv), "ecdsa"
    return {
        ...
        "req_content": "ticket,path,timestamp",
        "req_sign": req_sign,
        "timestamp": timestamp,
    }
```

**核对结果**：

| 维度 | 文章 | 项目 |
|---|---|---|
| ecdh_key 来源 | 私钥 + 服务端证书 | ✅ `derive_ecdh_key(prv, server_cert)` |
| 算法 | 未明说 | ✅ ECDH-P256 + HKDF-SHA256 |
| 变化字段 | `req_sign` + `datestamp` | ✅ `req_sign` + `timestamp` |
| 被签内容 | 未明说 | ✅ `ticket={ticket}&path={api}&timestamp={ts}` |
| 签名算法 | 未明说 | ✅ HMAC-SHA256（主）/ ECDSA（兜底） |

**项目远超文章。** 文章只给了「要算 req_sign」这个方向，项目把被签内容、算法、两种模式的切换条件全解出来了。

**但注意**：这条路需要 `ticket` + `server_cert` + `prv` 三样，**全部依赖扫码登录**。

### 2.4 `x-tt-session-dtrait`

这是全文最详细的部分，也是**项目实现最完整的地方**。

**文章说（外层格式）**：

> 结果格式为：`"d0_xx_xx"`
> `d0` 固定，第一个 `xx` 为 rsa 加密，第二个 `xx` 为 aes-cbc 加密
> 在发布页面（编辑页面）时 会随机生成一个 aeskey，再通过 rsa 把 key 加密 放到第一个 `xx`
> 然后再随机生成一个 iv，通过 aes 把一段内容通过刚刚的 key + iv 加密

**项目实现**（`utils/dtrait.py:9-13`）：

```
<pk1_version>_<base64(RSA_PKCS1v15(pk1, aes_key_hex))>_<base64(iv + AES128_CBC(payload))>

- `aes_key_hex`：16 字节随机数的 32 位小写十六进制字符串，RSA 加密的正是这个字符串本身
- AES：AES-128-CBC + PKCS7，密钥取 `bytes.fromhex(aes_key_hex)`，IV 随机 16 字节并前置到密文
- `payload`：`{"dtrait":<设备特征blob>,"timestamp":<秒级>,"sdkVersion":<ver>,"path":<pathname>}`
```

**核对结果**：

| 维度 | 文章 | 项目 |
|---|---|---|
| 格式 | `d0_xx_xx` | ✅ `<pk1_version>_<rsa>_<aes>` |
| 第一段 | RSA 加密 AES key | ✅ RSA PKCS#1 v1.5 |
| 第二段 | AES-CBC + 随机 IV | ✅ AES-128-CBC + PKCS7，IV 前置 |
| payload 内容 | `{"dtrait":...,"timestamp":...,"sdkVersion":...,"path":...}` | ✅ **字段完全一致** |
| RSA 公钥来源 | 通过接口获取，目前固定 | ✅ 项目也缓存 pk1 |

**文章原文明示 payload**：

```json
{"dtrait":"IAAAAA......","timestamp":1753688900,"sdkVersion":"1.0.31-beta.4","path":"/web/api/media/aweme/create_v2/"}
```

**项目文档字符串的字段顺序、含义完全对应。**

### 2.4 续：dtrait 内层数组（关键部分）

**文章说**：

> 最后是一个数组 通过 `fromCharCode` 再 base64
> 通过 vmp 日志分析，数组又是另外一个 object int 运算过来的

```python
keys = sorted(data.keys())
vmp_result = []
for key in keys:
    value = data[key]
    vmp_result.append(key)
    vmp_result.append((value >> 24) & 255)
    vmp_result.append((value >> 16) & 255)
    vmp_result.append((value >> 8) & 255)
    vmp_result.append(value & 255)
prepend = [32, 0, 0, 0, 0, 144]
new_arr = prepend + vmp_result
bytes_data = bytes(new_arr)
base64_str = base64.b64encode(bytes_data).decode('ascii')
```

> 数值分析，比如直接搜第 50 个 823932446
> 先获取 ua 再经过 `Oa` 这个函数计算，搜了一下 `Oa` 这个函数 就是 **mmh3 hash 算法**

**项目实现**（`utils/dtrait_features.py:170-192`）：

```python
def build_blob(profile, access_type=0):
    """生成内层 dtrait blob（base64 字符串）。

    :param access_type: central 用 0，edge 侧同样为 0（实测两者头字节都是 0x20）。
    """
    head = ((profile.get("reserved", 0) & 0x3) << 6) \
        | ((profile.get("dtrait_type", 1) & 0x1) << 5) \
        | ((access_type & 0x1) << 4) \
        | (profile.get("version", 0) & 0xF)

    values = dict(profile["render_hashes"])
    for n, s in computed_features(profile).items():
        values[n] = murmur3_32(s)

    body = bytearray()
    for n in range(1, 35):
        body.append(STR_TAGS[n])
        body += values[n].to_bytes(4, "big")

    blob = bytes([head]) + _bool_buffer(profile.get("bools", {})) + b"" + bytes(body)
    return base64.b64encode(blob).decode()
```

**核对结果**：

| 维度 | 文章 | 项目 |
|---|---|---|
| 结构 | `[prepend] + [key, 4字节大端值]...` | ✅ 完全一致的思路 |
| 每项 | `key` + 4 字节大端（`>>24, >>16, >>8, &255`） | ✅ `values[n].to_bytes(4, "big")` |
| 哈希算法 | `Oa` = **mmh3** | ✅ `murmur3_32(s, seed=0)` |
| prepend | `[32, 0, 0, 0, 0, 144]` | ⚠️ 见下方差异 |

**关键差异**：文章的 `prepend` 是硬编码的 `[32, 0, 0, 0, 0, 144]`，而项目：

```python
head = ((reserved & 0x3) << 6) | ((dtrait_type & 0x1) << 5) | ((access_type & 0x1) << 4) | (version & 0xF)
# 默认参数下 = (0<<6) | (1<<5) | (0<<4) | 0 = 0x20 = 32  ✅ 与文章第一个字节一致
blob = bytes([head]) + _bool_buffer(...) + b"" + bytes(body)
```

`0x20 = 32` 对上了。但文章后面的 `[0, 0, 0, 0, 144]` 在项目里是 `_bool_buffer()` 生成的 **bool 位图**，长度和内容取决于设备档案，不是固定 5 字节。

**项目更进一步**：文章只是观察到「prepend 是这几个数」，项目解出了头字节的位域构成（`reserved` / `dtraitType` / `accessType` / `version`）和 bool 位图的完整布局：

```
bool 位图：Uint8Array((floor(maxIdx/32)+1) * 5)，第 n 个 bool 落在
buf[5*(floor(n/32)+1) - floor((n%32)/8) - 1] 的第 n%8 位（见 VM 的 getBoolBuffer）
```

**另外项目还解出了字符串特征的 tag 映射**（文章完全没提）：

```python
STR_TAGS = {n: (31 + n if n <= 33 else 71) for n in range(1, 35)}
# str_1..str_33 -> 32..64, str_34 -> 71（见 VM 的 fn#177）
```

## 对我们当前问题的实际帮助

### ❌ 不能解决的

1. **扫码登录的 fpk1 问题** —— 文章完全没提 fpk1，它假设你有可用的浏览器环境
2. **`get_user_info` 的 0/8 失败** —— 文章只讲发布接口，不涉及读接口

### ✅ 有启发的一点

**2.2 节的这句话**：

> 浏览器里会存到 localStorage 里面……把它看成浏览器环境对应账号就好了……**把 e, r 都复制下来先**

这提示了一条我们**没试过**的路：

```
从 dyclaw 的 Chrome profile 里导出 localStorage 中的 e（私钥）和 r（公钥）
        ↓
让 Douyin_Spider 用这把「已被服务端信任的密钥」而不是自己生成新的
        ↓
配合该浏览器已有的 fpk1 / fpk2 / UA / dtrait
        ↓
可能绕过 fpk1 校验
```

**但仍有障碍**：

| 障碍 | 说明 |
|---|---|
| 需要 `ticket` / `ts_sign` | 这些在登录响应头里，localStorage 不一定有 |
| 密钥与 cookie 必须同源 | `ticket_matches_session()` 会校验 `ts_sign` 前缀与 cookie 里的 `bd_ticket_guard_ts_sign_id` 是否匹配 |
| 项目不支持导入 | `grep localStorage` 只出现在注释里，且都是说「不需要读浏览器 localStorage」 |

### 💡 另一个可能的收获

文章提到 **「连续发布第三条会掉号」**。这说明即使参数全对，**发布频率也是风控维度**。如果将来要测写接口，需要注意这一点。

## 建议

**这篇文章值得存档，但不必据此改动当前计划。**

理由：

1. 它验证了项目实现的正确性（间接说明项目质量可信）
2. 它的技术前提（已有可用浏览器环境）与我们的困境（无法建立可用环境）不同
3. 它唯一的新启发（复制 `e`/`r`）需要先解决「ticket 从哪来」，否则仍然卡在扫码登录

**如果将来要重启扫码登录攻坚**，优先级应该是：

```
1. 从 Chrome profile 导出 localStorage 的 e / r（文章 2.2 的提示）
2. 同时导出该浏览器的 fpk1 / fpk2 / UA（对齐设备身份）
3. 检查能否同时拿到 ticket / ts_sign（可能在 cookie 或响应头缓存里）
4. 若三者齐全，用 DY_FPK1 + 导入密钥重试扫码
```

**其中第 3 步是关键未知数。** 如果拿不到 ticket，这条路也走不通。
