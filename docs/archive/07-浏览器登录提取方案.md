## 1. 核心洞察

之前的所有困境（[03](03-扫码登录攻坚.md)、[04](04-get_user_info诊断.md)）都源于一个假设：

> 必须让 Douyin_Spider **自己生成密钥对**，走一遍完整的扫码登录。

但用户提出了一个更简单的思路：

> **像之前的项目一样，唤起浏览器进抖音自己的网站，我登录进去。**

这个思路正确的根本原因：

```
浏览器登录时，服务端已经把 ticket / ts_sign / client_cert
签发给「浏览器自己生成的那把密钥」

这套素材会持久化在：
  - localStorage（私钥、client_cert、ticket、ts_sign）
  - cookie（bd_ticket_guard_client_data、bd-web-sign-page-guard）

只要把它们提取出来注入 auth，就能复用浏览器已被信任的身份。
不需要扫码、不需要解决 fpk1。
```

## 3. 最难的一步：从 LevelDB 还原私钥

### 问题

Edge 的 localStorage 存在 LevelDB 里，**用了前缀压缩**。私钥文本被切成两段，中间插入控制字节：

```
ec_privateKey":"-<01><01>@BEGIN PRIVATE KEY<01><15>t-\nMIGHAgEAMBMGByqGSM49AgEGCC<0d><0c><f0><9a>wEHBG0wawIBAQQgVCBfA4N8...
```

直接按可见字符提取会得到：

```
<REDACTED-PRIVATE-KEY>...
```

**缺失了 `qGSM49AwEHBG0wawIBAQQg` 这 22 个字符**，导致 base64 解出来是畸形 DER。

### 解法：用 PKCS#8 标准前缀反推

P-256 的 PKCS#8 私钥前缀是**固定常量**：

```
标准前缀: <REDACTED-PRIVATE-KEY>已知片段: MIGHAgEAMBMGByqGSM49AgEGCC
缺失部分: qGSM49AwEHBG0wawIBAQQg   ← 22 字符
```

补齐后得到合法的 DER：

```
308187020100301306072a8648ce3d020106082a8648ce3d030107046d306b0201010420<32字节私钥>...
```

### 更简洁的解法：直接取 32 字节私钥

PKCS#8 结构里，`04 20` 之后就是**裸的 32 字节私钥**。对应 base64 是 43 字符 + 1 个补位：

```python
secret = "VCBfA4N8lMyQOBKBMBA7OOT7tqI/G2kiR8KE6HUDge2"   # 43 字符
raw = base64.b64decode(secret + "=")                     # → 32 字节
# raw.hex() = <REDACTED-32B-HEX>

from ecdsa import SigningKey, NIST256p
sk = SigningKey.from_string(raw, curve=NIST256p)
```

### 验证方法（关键）

**用推导出的公钥和已知公钥比对**，数学上等价即证明私钥正确：

```python
vk = sk.get_verifying_key()
point = b"\x04" + vk.to_string()
derived = base64.b64encode(point).decode()
# derived == "<REDACTED-PUBKEY-88-chars>"
# → True
```

实测通过，私钥 100% 正确。

## 6. 附带发现：一个掩盖真实错误的 bug

### 现象

排查过程中一直看到：

```
RuntimeError: 接口返回空响应（HTTP 200），通常是签名参数不对或被风控拦截。
```

但实际响应体是**有内容的**：

```json
{"extra":null,"log_pb":{"impr_id":"..."},"status_code":2,"status_msg":"UserId不合法","user":{}}
```

### 根因

两个问题叠加：

**问题 1：我用的 sec_uid 是截断的**

```
MS4wLjABAAAAeDtvYiEu_-NfwGGZTRjNH_FmZ24J           ← 少了后半段（我手抄的）
MS4wLjABAAAAeDtvYiEu_-NfwGGZTRjNH_FmZ24JM9eBGtLFmxFqVHd-bkv7dPKi4KK-DUu2JQbZ  ← 完整
```

**问题 2：`check_risk_response` 对 129 字节的响应判断错误**

`dy_apis/douyin_api.py` 的 `check_risk_response`：

```python
def check_risk_response(resp):
    text = (resp.text or "").lstrip()
    if text.startswith("{") or text.startswith("["):
        return          # ← 本该在这里返回
    ...
    if not text:
        raise RuntimeError(f"接口返回空响应（HTTP {resp.status_code}）...")
```

理论上 JSON 响应会正常返回。但实测中**有些 129 字节的响应被误判为空响应**——推测是响应头里带了 `X-Tt-Verify-Passport-Decision`，走了前面的分支。

### 建议

排查这类问题时，**先打印原始响应体和 status_msg**，不要只看异常信息：

```python
r = requests.get(...)
print(r.status_code, len(r.content), r.content[:300])
```

这能避免被「签名参数不对」的提示误导。

## 7. 与其他方案的对比

| 方案 | 可行性 | 说明 |
|---|---|---|
| 扫码登录（项目自带） | ❌ | fpk1 设备指纹不匹配，34 秒触发限频 |
| 仅贴 cookie | ⚠️ | 读能力 80%，用户主页 0/8 |
| **浏览器登录 + 提取素材** | ✅ | 读能力完整，用户主页 6/8 |
| 从 localStorage 导入私钥（本文） | ✅ | 见上 |

### 为什么这个方案优于扫码

```
扫码：项目生成新密钥 → 服务端不信任新设备指纹 → 限频
浏览器：浏览器生成密钥 → 服务端已签发 ticket 给这把密钥 → 提取即用
```

**浏览器登录产生的身份是「已被服务端信任」的**，直接复用比重建更可靠。

## 8. 提取步骤（可复现）

### 前提

用 Edge/Chrome 打开抖音并完成登录，profile 目录保留。

### 定位 leveldb

```
<profile>/Default/Local Storage/leveldb/
├── 000005.ldb    ← 私钥、server_cert 在这里
├── 000143.ldb    ← client_cert、ticket、ts_sign 在这里
├── 000141.log    ← WAL（可能含未压缩数据）
└── ...
```

### 提取流程

```python
# 1. 读所有 ldb/log 文件为 bytes
# 2. 找 b"ec_privateKey"，在其后 800 字节内
#    提取 "VCBfA4N8..." 形态的 43 字符 base64 → 32 字节私钥
# 3. 找 b"sign_data_key/web_protect"，
#    正则抓 "ticket" 和 "ts_sign" 的转义 JSON 值
# 4. 找 b"s_sdk_cert_key"，抓 "pub.xxx" 形态的 client_cert
# 5. 用 ecdsa 从 32 字节私钥构造 SigningKey，
#    推导公钥并与 cookie 里 bd_ticket_guard_client_data 的
#    ree_public_key 比对，验证正确性
```

### 注意

- **LevelDB 前缀压缩**：私钥文本会被切断，必须用 PKCS#8 标准前缀或 32 字节直接提取
- **不要用可见字符过滤后直接拼接**，会丢失被压缩的片段
- **必须验证**：私钥 → 公钥 → 与已知公钥比对

## 10. 已实现的工具：`browser_credential.py`

提取流程已固化为项目根目录的 `browser_credential.py`。

### 用法

```bash

python browser_credential.py --profile <dir>  # 指定 profile 目录
python browser_credential.py --list           # 只列出找到的 profile
python browser_credential.py --dry-run        # 提取但不写 .env
```

### 实测输出

```
扫描 1 个 profile（最近修改优先）...
  ...\255499049641192.profile  命中 4 项
      ['private_key_pem', 'ticket', 'ts_sign', 'client_cert']

采用: ...\255499049641192.profile

提取结果:
  私钥        54205f03837c94cc9038128130103b38...
  推导公钥    <REDACTED-PUBKEY>...
  公钥验证    通过
  ticket      hash.<REDACTED-48-chars>...
  ts_sign     ts.<ver>.<REDACTED-48-chars>...
  client_cert pub.<REDACTED-48-chars>...

已写入: ...\Douyin_Spider\.env
```

### 实现要点

**1. 私钥用「滑窗 + 公钥验证」而非字符串拼接**

DER 里的公钥和 cookie 里的 base64 **起始偏移不同**：

```
cookie:  <REDACTED-PUBKEY>...
DER 内:    DQgAE<REDACTED>...（同一把公钥，但 base64 起点不同）
```

所以不能直接比字符串。脚本把所有候选 base64 解码成原始字节，再比对
`b"\x04" + vk.to_string()` 是否出现在其中。

**2. PEM 用 `b64:` 前缀单行存进 .env**

`.env` 按行解析，多行 PEM 直接写会被拆散。`python-dotenv` 也**不会**把
`\n` 转义还原成换行——实测读回来是字面量 backslash-n，`SigningKey.from_pem`
直接报 `UnexpectedDER Empty string does not encode a sequence`。

最终方案：写入时 `b64:<base64>`，读取时在 `utils/common_util.py` 的
`_env_multiline()` 里还原：

```python
def _env_multiline(name):
    raw = os.getenv(name)
    if not raw:
        return None
    if raw.startswith("b64:"):
        return base64.b64decode(raw[4:]).decode("utf-8")
    return raw
```

`load_env()` 里 `private_key=_env_multiline('DY_PRIVATE_KEY')`。

### 对项目的改动

| 文件 | 改动 |
|---|---|
| `browser_credential.py` | 新增，提取工具 |
| `utils/common_util.py` | 新增 `_env_multiline()`，`load_env()` 改用它读 `DY_PRIVATE_KEY` |

**兼容性**：`_env_multiline` 对非 `b64:` 开头的值原样返回，不影响手工填写单行私钥的旧用法。
