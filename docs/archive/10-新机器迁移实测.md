### 2.1 结论先行：Edge 这条路走不通

## 3. P2 · profile/self 判据：通过

### 3.1 文档 [09](09-迁移到新机器指南.md) 的探针有缺陷

[09](09-迁移到新机器指南.md) §2.7 给的探针是**裸请求，不带签名**：

```python
r = rq.get('https://www.douyin.com/aweme/v1/web/user/profile/self/', cookies=a.cookie, verify=False)
```

实测这个探针**永远返回「用户未登录」**，与 blocked 与否无关——因为缺 `a_bogus` / `msToken` / `uifid` 等签名参数。用它会得到假阴性。

**正确做法**：走项目的签名栈。

```python
import dy_apis.douyin_api  # 必须先导入，规避循环导入
from utils.common_util import load_env
from builder.header import HeaderBuilder, HeaderType
from builder.params import Params
import utils.http_client as rq

a = load_env()
headers = HeaderBuilder.build(HeaderType.GET)
headers.with_bd_readonly(a)
headers.with_csrf(a.cookie_str)
headers.with_uifid(a)
headers.set_header('referer', 'https://www.douyin.com/')
params = Params()
params.with_platform(round_trip_time='0')
params.with_web_id(a, 'https://www.douyin.com/')
params.with_uifid(a)
params.with_verify_fp(a)
params.add_param('msToken', a.msToken)
params.with_a_bogus()

r = rq.get('https://www.douyin.com/aweme/v1/web/user/profile/self/',
           params=params.get(), headers=headers.get(), cookies=a.cookie, verify=False)
print(r.json().get('status_code'), r.json().get('status_msg'))
```


**与老机器对照**：

**判定：[08](08-写接口测试与blocked分析.md) §7 的推断成立——blocked 是老机器的 IP / 设备级限制。**

### 3.3 凭证失效已定位：写请求会作废会话 ticket

**第一轮（10:13）**：

| 时间 | 事件 |
|---|---|
| 10:13:40 | profile/self **成功**（`status_code: 0`） |
| 10:14:09 | 第一次 digg 调用（`check_risk_response` 报 403） |
| 10:14:38 | 手工 digg 诊断（`key-sign-result: 2`） |
| 10:16:08 起 | profile/self **稳定失败**，`status_code: 8 用户未登录` |

**第二轮（10:32，对照实验）**：重新登录 360 取全新凭证，**全程不发任何写请求**。

| 时间 | 动作 | 结果 |
|---|---|---|
| 10:32:56 | 写入全新凭证（`ticket hash.5xW9F7…`、`ts_sign ts.2.645de8…`、63 cookie） | — |
| 10:33 | profile/self ×3（间隔 3s） | **3/3 通过**，`status_code=0`，`key-sign-result` 未出现 |
| 10:33 | get_work_info | OK（digg_count 43213 / 782 评论） |
| 10:33+20s | profile/self 再测 | **仍通过** |

**结论：**

1. **凭证没有时效问题**——间隔 20 秒、3 次连续请求均正常
2. **是写请求作废了会话 ticket**——第一轮唯一变量就是那次 digg
3. 作废后 `profile/self` 从 `status_code: 0` 变为 `status_code: 8 用户未登录`，与 `digg` 的失败码**完全一致**

**已排除的干扰项**：

- 写法差异（`HeaderBuilder().build()` vs `HeaderBuilder.build()`，`build` 是 staticmethod，等价）
- msToken 过期（`auth.msToken` 有 TTL 自动续期，重取后仍失败）
- csrf token（重新 `generate_csrf_token` 后仍失败）
- 凭证不自洽（三者已验证一致，见 §2.4）

**推论**：`key-sign-result: 2` 不是「凭证坏了」，而是「这次写请求的 ticket 签名没通过」。作废是**后果**而非原因。真正的根因仍需在签名算法层面深挖（见 §8）。

## 4. P3 · 写接口：`key-sign-result: 2`

### 4.1 文档 [08](08-写接口测试与blocked分析.md) 的「403」是误判

[08](08-写接口测试与blocked分析.md) §3 记录 `点赞失败: RuntimeError: 接口返回空响应（HTTP 403）`。

实测**真实响应是 HTTP 200**，`check_risk_response` 把空 body 当成了风控。完整响应头才是关键：

```
HTTP 200
bd-tt-error-code: 8
bd-ticket-guard-key-sign-result: 2
bd-ticket-guard-sign-res-static-ts-sign: 1102
bd-ticket-guard-sign-res-static-sign: 1102
body: {"status_code":8,"status_msg":"用户未登录","log_pb":{...}}
```

`bd-ticket-guard-key-sign-result: 2` 是**服务端明确告知 ticket 签名校验失败**。

### 4.2 已做的对照实验

| 变量 | 结果 |
|---|---|
| `digg` 用 `with_bd_readonly()`（4 头，无 client-data） | `key-sign-result: 2` |
| `digg` 用 `with_bd()`（完整，**含 `bd-ticket-guard-client-data`**） | **完全相同** |
| `digg type=1`（点赞） | 同上 |
| `digg type=0`（取消） | 同上 |

**结论：不是缺 client-data，不是方向问题。**

### 4.3 读能力仍然完好

```
get_work_info  → OK, desc: "2026 年10月 | 缩量周期第二阶段初期淘汰赛历史回思..."
                 digg_count: 2358
```

对照实验中发现：手工探针打 `aweme/detail` 返回 `403 Blocked by ArgusSecurityPlugin Signature Not Found`，但项目封装的 `get_work_info` 正常——因为后者带了 secsdk webSign（`utils/secsdk_web_sign.py`）。**手工探针必须走 `Params.sign()` 才不会被 Argus 拦。**

同批 `Device Bound Sessions` 也被重写。**影响范围是所有站点，不只是抖音。**

### 5.2 原因

在 §2.2 的 CDP 实验中，反复用 `--user-data-dir` 指向**真实** Edge profile 启动无头 / 带窗口 / 目录联接实例，并多次 `Stop-Process -Force`。Edge 在这些非正常启动路径下重建了 cookie 存储。

### 5.3 教训

**永远不要对真实浏览器 profile 做实验性启动。** 正确做法：

1. 先复制 profile 到临时目录（注意 App-Bound 会导致解密失败，此时应直接判定该浏览器不可用）
2. 或干脆换一个不启用 App-Bound 的浏览器（如 360）
3. 需要退出浏览器时，让用户自己退出，不要 `Stop-Process`

leveldb 里 `000126.ldb` 仍有 8 月旧 ticket 记录，但 `client_cert` 与当前私钥不匹配，**是毒凭证，不可用**。

## 6. 代码修复：`browser_credential.py`

本次共 3 处修改（`+88 / −20`，**尚未提交**）。

### 6.1 `extract_ticket_and_sign`：支持新版 leveldb 键名

**问题**：Edge / 360 新版把键名从 `sign_data_key/web_protect` 改为 `security-sdk/s_sdk_sign_data_key/<scope>`，值是整段 JSON：

```
security-sdk/s_sdk_sign_data_key/login
{"ticket":"hash.V8rTSNm+...","ts_sign":"ts.2.ea41b...","client_cert":"pub.BPtq...","create_time":1793238595}
```

且旧锚点会被 leveldb 前缀压缩切断成 `sign_ArA\x854/web_protect`，`data.find(b"sign_data_key/web_protect")` **永远返回 -1**。

**修复**：
- 新增 `_iter_sign_records()` 解析新格式（处理 `\\"` 转义）
- 旧格式改为按 `web_protect` 后缀匹配
- 同一 profile 会残留多份历史记录，各自绑不同私钥。**按 `client_cert` 与已推导公钥的匹配度打分，再用 `create_time` 兜底取最新**——注入错的那份服务端必判不匹配

### 6.2 `_decrypt_cookie_value`：App-Bound 明确报错

**问题**：`v20` 密文被当作明文返回，产生 `UIFID_TEMP=v20+;…` 这类**看似有值的乱码**，调用方会误以为提取成功（实测 Edge 62 个 cookie 全部如此）。

**修复**：`v20`/`v21` 抛 `AppBoundEncryption`；`extract_cookies` 聚合后给出「该 profile 的 N 个 cookie 全部是 App-Bound 加密，换用未启用该加密的浏览器」。

### 6.3 新增 360 极速浏览器

`BROWSERS` 加入 `("360 ChromeX", r"D:\Software\0-9\360ExtremeBrowser\360ChromeX\Chrome\User Data")`。

### 6.4 已知缺陷（未修）

`running_chrome_user_data_dirs()` 依赖 `wmic`，而 **Windows 11 build 26300 已移除 wmic**，异常被 `except Exception: return []` 静默吞掉。应改用 `Get-CimInstance Win32_Process`。
