# 03 · 扫码登录攻坚

> 记录时间：2026-10-25 ~ 2026-10-28
> 结论：**失败**。根因是 fpk1 设备指纹，与冷却时间无关。

---

## 1. 为什么关注扫码登录

Cookie 路径下 `auth.ticket` / `private_key` / `ts_sign` 全部为空。这导致：

- `get_user_info` 100% 失败（详见 04）
- 所有写接口不可用（`publish_comment` / `digg` / `collect_aweme` / 创作者中心）

### 为什么 cookie 带不来这些

关键在于 `utils/passport.py:55`：

```python
def generate_ec_keypair():
    """生成 bd-ticket-guard 用的 P-256 密钥对（PEM）。"""
    sk = SigningKey.generate(curve=NIST256p)
    return sk.to_pem().decode(), sk.get_verifying_key().to_pem().decode()
```

**私钥不是服务端给的，是本地生成的。** 完整流程：

```
1. 本地生成 P-256 密钥对
2. build_client_data_cookie(private_key)
   → 把公钥写进 bd_ticket_guard_client_data cookie
3. 带着这个 cookie 去取二维码
4. 服务端把 ticket/ts_sign/client_cert 签给「这把公钥」
5. 之后每个写请求用私钥算 bd-ticket-guard 签名
```

`login_api.py:1319` 的注释说明了必要性：

> 公钥必须在**取二维码之前**就通过 Cookie 交给服务端……缺了这个 Cookie，扫码能成功、Cookie 能落，但响应里永远没有 `bd-ticket-guard-server-data`，于是拿不到 ticket/ts_sign——后续 create_v2、发评论这类强校验接口就全都做不了。

**所以：浏览器 cookie 绑在浏览器的私钥上，复制 cookie 不会复制私钥。项目明确不支持从 localStorage 导入私钥（`grep localStorage` 只出现在注释里，且都是说「不需要读」）。**

## 3. 根因：fpk1 用的是内置 fixture

### 日志证据

每次启动都有这条警告：

```
WARNING | dy_apis.login_api:_add_page_cookies:1747 -
未捕获当前浏览器 fpk1，已使用项目内 FingerprintJS fixture 纯算；
如遇风控，请提供同一设备的 DY_FPK1 或组件文件
```

### 源码说明

`dy_apis/login_api.py:1712-1720`：

```python
# fpk2 is a true pure rule: lowercase MD5 of the full User-Agent.
# fpk1's *algorithm* is known, but its inputs are device-bound
# FingerprintJS values (canvas/fonts/WebGL/audio/plugins).  The
# project ships one captured component fixture so a clean, browserless
# install can still attempt phone login.  It is a compatibility
# fallback, not proof of the caller's physical device; callers with a
# browser capture should continue to provide DY_FPK1 (or a matching
# DY_FP_COMPONENTS_FILE).
```

翻译：**fpk1 算法已知，但输入是设备绑定的**（canvas / 字体 / WebGL / 音频 / 插件）。项目内置的是一份抓取样本，属于「兼容性 fallback，不是调用者物理设备的证明」。

### 这意味着什么

我们拿**别人设备的指纹样本**去登录，服务端识别出指纹与实际环境不一致，直接限频。

## 4. 一个反直觉的发现

本机已有的登录态里**确实存着真实的 fpk1**：

```
dyclaw 会话 cookie 数: 64
  含 fpk1 : True
  含 fpk2 : True
项目 fixture fpk1 len: 88
```

但存在两个障碍：

### 障碍 1：UA 不一致

```
fixture UA: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/1...
dyclaw UA:  Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/1...
UA 是否一致: False
```

前 75 字符相同但**并不完全一致**。而 `fpk2 = md5(完整 UA)`，如果 UA 对不上，fpk1 和 fpk2 就来自不同设备，服务端一验就露馅。

### 障碍 2：密钥是新的

Douyin_Spider 扫码时**自己生成新的 P-256 密钥对**，而 `bd_ticket_guard_client_data` 绑在这把新密钥上。旧的 fpk1 是浏览器登录时产生的，与项目新生成的会话状态天然不匹配。

**这是一个结构性矛盾**：要么整套设备身份（UA + fpk1 + fpk2 + dtrait + 屏幕尺寸）都对齐到同一台设备，要么就回到浏览器。

## 5. 限频参数（供参考）

`dy_apis/login_api.py:843-850`：

```python
QR_TTL = 55              # 二维码 55 秒换一张
THROTTLE_GIVEUP = 120    # 连续限频超过 120 秒就报错退出
POLL_INTERVAL = 5.2      # 每 5.2 秒轮询一次
MS_COMMON_INTERVAL = 300.0
```

每张码存活 55 秒，期间轮询约 10 次。项目自己的注释也警告过这个坑：

> 2026-08-17 实测踩过：被限频（error_code=7）期间状态读不到，代码仍按 55 秒兜底换了码，而用户正好扫的是那张 —— **扫码直接作废**，界面上表现为「我扫过了它还一直弹新码」。

## 6. 调试工具（本次自建）

### `_login_qr.py`

在项目原生 `qrcode_login` 基础上，唯一改动是给 `check_qrcode` 打补丁，把每次轮询的真实 status 写进 `_login_status.json`：

```python
_orig_check = api.check_qrcode

def check_qrcode(auth, token):
    res = _orig_check(auth, token)
    data = (res or {}).get("data") or {}
    if data.get("error_code") == 7:
        _state["phase"] = "throttled"
    elif data.get("status") == "scanned":
        _state["phase"] = "scanned"     # ← 这是原生代码看不到的中间态
    ...
    return res

api.check_qrcode = check_qrcode
```

**价值**：原生 `qrcode_login` 只打印「二维码到期，换一张」，看不出用户到底扫没扫。打补丁后能区分 `waiting_scan` / `scanned` / `confirmed` / `throttled`。

### `_login_qr_viewer.html`

自动刷新的查看页，每 2 秒轮询 `_login_status.json`，二维码过期自动换新。

**必须用 HTTP 服务器打开**，因为 Chrome 在 `file://` 协议下会阻止 `fetch`：

```bash
python -m http.server 8777 --bind 127.0.0.1
```

## 7. 结论

| 判断 | 结论 |
|---|---|
| 是冷却时间不够吗？ | **否**。间隔 3 天仍在 34 秒触发 |
| 是代码 bug 吗？ | **否**。这是设计取舍，注释里写得很清楚 |
| 是用户操作问题吗？ | **否**。第 3 轮确认浏览器正常、页面正常轮询 |
| 上游有修复吗？ | **否**。`git fetch` 后与 origin/master 完全一致 |

**唯一可能的突破口**：从本机 Chrome 抓取完整的一套设备身份（fpk1 + fpk2 + UA + dtrait），但仍有「新密钥 vs 旧指纹」的结构性矛盾。
