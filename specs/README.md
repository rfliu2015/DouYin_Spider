# specs —— 需求规格与实施计划

> 本目录按**需求**组织，而不是按知识主题组织。
> 一个需求 = 一个子文件夹；文件夹内放该需求的需求文档、实施计划与验收记录。

---

## 这个目录是做什么的

`docs/` 记录的是"研究结论"（我们验证过什么、为什么不通）。
`specs/` 记录的是"要做的东西"（用户想实现什么、拆成哪些功能、怎么验收）。

两者互补：

| | `docs/` | `specs/` |
|---|---|---|
| 出发点 | 逆向研究 | 业务需求 |
| 内容 | 能力现状、签名原理、踩坑记录、未解问题 | 目标、功能拆解、可行性评估、待确认问题、验收标准 |
| 粒度 | 按主题（环境/签名/读能力/写能力…） | 按需求（一个需求一个文件夹） |
| 生命周期 | 长期维护，随实验更新 | 需求交付后归档，编号不复用 |
| 写代码时看哪个 | 查"这个接口为什么这样调" | 查"这一步要产出什么、怎么算做完" |

一句话：**`docs/` 是研究笔记与结论，`specs/` 是按需组织出的功能规格与实施计划。**
本目录不复制 `docs/` 的结论，只引用；技术细节以 `docs/` 为准。

## 命名约定

```
specs/
├── README.md            ← 你在这里（总索引 + 约定）
├── 01-推荐流采集/
│   └── 需求.md
├── 02-<简短名称>/
│   └── 需求.md
└── ...
```

- 子文件夹名格式：`NN-简短名称`，`NN` 是两位数字，从 `01` 开始递增。
- `NN` **只增不减、不复用、不重排**。需求作废就保留编号并在本索引标记"已废弃"，不要让 02 变成 01。
- 名称用中文短词，2~6 个字，不要空格、不要标点、不要括号。
- 每个需求文件夹至少包含一个 `需求.md`；实施阶段可在同一文件夹内追加计划与验收文档（如 `实施计划.md`、`验收记录.md`），不要散落到仓库其他地方。
- 需要技术验证的方案（如选型、可行性实测）单独写成 `技术方案-<主题>.md`，与 `需求.md` 并列，不要把验证过程塞进需求文档。
- 需求之间不嵌套：`02` 不是 `01` 的子需求，是并列的另一个需求。

> 注：本目录叫 `specs/` 而不是 `requirements/`，因为仓库根目录已有 `requirements.txt`（Python 依赖清单），叫 `requirements/` 会混淆。

## 新增一个需求的步骤

1. 取下一个未使用的编号 `NN`，新建 `specs/NN-简短名称/`。
2. 写 `需求.md`：一句话目标 → 功能拆解 → 每条功能的已知可行性 → 待确认问题 → 验收标准建议。
3. 在本文档的"当前索引"表里加一行。
4. 待确认问题清空、验收标准认可后，才进入实施计划阶段。
