# 扫码登录

> 定论文档。**结论：此路不通**，已被 [凭证提取](T03-凭证提取.md) 方案绕过。
> 保留本文仅为记录根因，避免重复踩坑。

---

## 1. 结论先行

| 项 | 结果 |
|---|---|
| 纯 HTTP 扫码登录 | ❌ **失败** |
| 根因 | `fpk1` 使用内置 fixture，服务端识别出设备指纹不真实 |
| 4 轮尝试 | 全部失败，包括间隔 3 天重试 |
| 绕过方案 | [凭证提取](T03-凭证提取.md)（已成功） |

---

## 2. 为什么扫码登录重要

扫码登录会由项目自己生成 P-256 密钥对，从而拿到完整的 `bd-ticket-guard` 素材（写接口必需）。

**cookie 带不来这些**：私钥是本机生成的，不会跟 cookie 一起复制。

---

## 3. 根因：fpk1 用内置 fixture

项目源码注释（`utils/fingerprint.py`）：

```
fpk2 is a true pure rule: lowercase MD5 of the full User-Agent.
fpk1's *algorithm* is known, but its inputs are device-bound
FingerprintJS values (canvas/fonts/WebGL/audio/plugins).  The
project ships one captured component fixture so a clean, browserless
install can still attempt phone login.  It is a compatibility
fallback, not proof of the caller's physical device; callers with a
browser capture should continue to provide DY_FPK1 (or a matching
DY_FP_COMPONENTS_FILE).
```

**含义**：
- `fpk2` = UA 的 MD5，纯规则，**可以算**
- `fpk1` = 依赖 canvas / 字体 / WebGL / audio / plugins 等设备特征，**算不出来**，项目只能内置一份抓来的样本

→ 服务端能识别出这是「同一份样本」，判定为可疑设备。

---

## 5. 两个反直觉的发现

### 5.1 UA 不一致

项目生成的 UA 与 fpk1 fixture 采集时的 UA 不一致，加剧了可疑度。

### 5.2 密钥是新的

即使 fpk1 侥幸通过，新生成的 P-256 密钥与旧设备指纹也不匹配。

> **这两点说明：即使解决 fpk1，扫码登录仍有结构性矛盾。**

---

## 6. 如果想尝试这条路

需要解决 fpk1 设备指纹：

1. 从本机 Chrome 抓取完整设备身份（fpk1 + fpk2 + UA + canvas/WebGL/字体样本）
2. 写成 `utils/challenge_profile.json` 格式
3. 通过 `DY_FP_COMPONENTS_FILE` 指定

**但**：仍需解决「新生成的 P-256 密钥 vs 旧指纹」的矛盾。

**风险**：限频（`error_code=7`）是服务端冷却，**反复重试会加重**。实测间隔 3 天仍会触发。

---

## 7. 为什么不推荐

| 对比项 | 扫码登录 | 凭证提取 |
|---|---|---|
| 可行性 | ❌ 卡在 fpk1 | ✅ 已验证 |
| 需要浏览器 | ✅ 要真实浏览器环境 | ✅ 要（但只需登录一次） |
| 密钥新鲜度 | 新生成（不匹配） | 浏览器原生（已被信任） |
| 实现复杂度 | 需解决 fpk1 + 密钥矛盾 | 只需读 leveldb |

**凭证提取方案在每一项上都更优。**
