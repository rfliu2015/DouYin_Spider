# 凭证提取

> 定论文档。从浏览器 leveldb 提取 `bd-ticket-guard` 素材的原理与工具用法。
> **这是绕过扫码登录 fpk1 的关键方案。**

---

## 1. 为什么需要这条路

扫码登录会由项目自己生成 P-256 密钥，但服务端不认识这个新设备指纹（fpk1 用的是内置 fixture），轮询约 30 秒就返回 `error_code=7` 限频。详见 [扫码登录](T06-扫码登录.md)。

**而浏览器登录时，服务端已经把 ticket / ts_sign / client_cert 签发给浏览器自己生成的那把密钥**，这套素材持久化在 leveldb 里。提取出来注入 auth，就能复用「已被服务端信任」的身份。

---

## 2. 三处素材存放位置

| 素材 | leveldb 键名（新版） | 格式 |
|---|---|---|
| `ec_privateKey` | `security-sdk/s_sdk_crypt` | 43 字符 base64 → 32 字节私钥 |
| `ticket` + `ts_sign` | `security-sdk/s_sdk_sign_data_key/<scope>` | **整段 JSON** |
| `client_cert` | `security-sdk/s_sdk_cert_key` | `pub.xxx` |

### 2.1 新版 JSON 值（关键）

```
security-sdk/s_sdk_sign_data_key/login
{\\"ticket\\":\\"hash.V8rTSNm+...\\",\\"ts_sign\\":\\"ts.2.ea41b...\\",\\"client_cert\\":\\"pub.BPtq...\\",\\"create_time\\":1793238595}
```

> ⚠️ leveldb 里值是**转义过的 JSON**（`\\"` 而非 `"`），解析前必须 replace。

### 2.2 旧版键名（仍可能共存）

```
sign_data_key/web_protect
```

**坑**：leveldb 的前缀压缩会把它切断成 `sign_ArA\x854/web_protect`，导致 `data.find(b"sign_data_key/web_protect")` **永远返回 -1**。

> **正确做法**：按 `web_protect` 后缀匹配，不要匹配完整键名。

### 2.3 多份历史记录的取舍

同一 profile 会残留多个 scope 的记录（`login` / `web_protect` 等），**各自绑着不同的私钥**。

注入错的那份，服务端会认为 ticket 与私钥不匹配，写接口必失败。

**取舍规则**（`browser_credential.py` 已实现）：
1. 按 `client_cert` 是否等于`"pub." + 已推导公钥` **打分**
2. 同分时按 `create_time` 取最新

## 3. 浏览器加密方案对照（最重要的一节）

**不同浏览器用不同加密，直接决定能否提取。**

| 浏览器 | `os_crypt` 键 | cookie 前缀 | 可解性 | 结论 |
|---|---|---|---|---|
| **Edge 136+** | 含 `app_bound_encrypted_key` | `v20` | ❌ 主密钥 SYSTEM 级保护 | **不可用** |
| 便携 Chrome | 仅 `encrypted_key` | — | ❌ `err=87`（37 字节非标准裸密钥） | 不可用 |
| 用户 Chrome | 仅 `encrypted_key` | `v10` | ✅ | 可用 |
| **360 极速** | 仅 `encrypted_key` | `v10` | ✅ | **推荐** |

### 3.1 Edge App-Bound 的三层证据

```
os_crypt 键: ['app_bound_encrypted_key', 'aster_app_bound_encrypted_key',
              'audit_enabled', 'encrypted_key']
cookie 前缀: Counter({b'v20': 62})        ← 全部 v20
encrypted_key (用户 DPAPI) → 解密成功，32 字节
用该密钥解 v20           → 0 / 66          ← 完全解不开
app_bound_encrypted_key  → CryptUnprotectData err=-2146893813（SYSTEM 级）
IElevator COM            → CoCreateInstance hr=0x80040154（未注册）
是否管理员               → False
```

**结论：Edge 156+ 的 cookie 无法在普通用户权限下离线解密。**

### 3.2 CDP 方案为何也不行

用浏览器自身解密（`Storage.getCookies`）遇到两道墙：

1. **调试端口禁止默认目录**
   ```
   DevTools remote debugging requires a non-default data directory.
   ```
   Chromium 136+ 硬限制。

2. **复制 / 联接 profile 后 App-Bound 解密失败**
   - 目录联接（junction）→ CDP 可用，拿到 53 cookie，但 `sessionid`/`UIFID` **缺失**
   - 复制 profile → 39 cookie，`ttwid` 有，`sessionid` **缺失**
   - 原因：App-Bound 把密文**绑定到原始 `user-data-dir` 路径**

> 🚨 **血泪教训**：这套 CDP 实验对**真实 profile** 反复启动/强杀，导致 Edge 的 Cookies 库被整表清空。
> **永远不要对真实浏览器 profile 做实验性启动。** 详见 [未解问题](../状态/S03-未解问题.md)。

### 3.3 应急判断脚本

```python
import json, os, base64
ud = r'<browser user data dir>'
oc = json.load(open(os.path.join(ud, 'Local State'), encoding='utf-8'))['os_crypt']
print('app_bound:', 'app_bound_encrypted_key' in oc)   # True → 大概率不可用
```

## 4. 私钥还原原理

### 4.1 难点

LevelDB 用了前缀压缩，私钥文本会被切成两段并在中间插入控制字节。直接按可见字符过滤拼接会丢掉 `qGSM49AwEHBG0wawIBAQQg` 这类片段，解出来是畸形 DER。

### 4.2 解法：滑窗 + 公钥验证

把每个 **43 字符窗口**当作 32 字节私钥，推导公钥后与 DER 里内嵌的公钥（或 cookie 里的 `ree_public_key`）比对，**只有数学上一致才算命中**。

```python
from ecdsa import SigningKey, NIST256p
sk = SigningKey.from_string(raw32, curve=NIST256p)
derived = base64.b64encode(b'\x04' + sk.get_verifying_key().to_string()).decode()
# derived 必须等于 cookie 里 bd_ticket_guard_client_data 的 ree_public_key
```

> 暴力滑窗能成功的前提：私钥是 32 字节定长，且公钥可验证。这一步是**数学证明**，不是猜测。

## 5. 一致性校验（必做）

提取后**必须**做三项交叉验证，否则会拿到「毒凭证」：

| 校验 | 方法 | 失败含义 |
|---|---|---|
| 公钥验证 | `client_cert == 'pub.' + 私钥推导公钥` | 私钥与证书不配对 |
| 会话一致 | `ticket_matches_session()`（`ts_sign` vs cookie `bd_ticket_guard_ts_sign_id`） | ticket 与 cookie 非同一登录 |
| 可读性 | 所有 cookie 值均为可打印 ASCII | 解密失败（App-Bound 的乱码陷阱） |

> ⚠️ `ticket_matches_session()` **不检查** `client_cert` 与私钥是否配对，这一项要自己加。

## 6. 工具用法

见 [工具手册](T07-工具手册.md) §2。

**快速命令**：

```powershell
# 先看有哪些 profile
python browser_credential.py --list

# 试提取（不写盘）
python browser_credential.py --profile "<profile 目录>" --dry-run

# 正式写入 .env
python browser_credential.py --profile "<profile 目录>"
```

## 7. 写入 `.env` 的格式

```bash
DY_TICKET='hash.xxx'
DY_TS_SIGN='ts.2.xxx'
DY_CLIENT_CERT='pub.xxx'
DY_PRIVATE_KEY='b64:LS0tLS1CRUdJTi...'   # PEM 多行必须压成单行 base64
DY_COOKIES='UIFID_TEMP=...; ...'
```

**`DY_PRIVATE_KEY` 的 `b64:` 前缀**是约定的编码标记，由 `utils/common_util.py` 的 `_env_multiline()` 还原。

> 不能直接写多行 PEM：`python-dotenv` 会读成字面量 `\n`，`SigningKey.from_pem` 直接失败。

## 8. 时效性风险

**主流浏览器正在关闭这条路。**

| 浏览器 | 状态 |
|---|---|
| Edge 156 | ❌ 已关闭 |
| Chrome 136+ | ⚠️ 逐步启用 App-Bound |
| 360 极速 23.x | ✅ 尚未启用 |

随着浏览器升级，可选浏览器会越来越少。

**但读能力不受影响**——读接口只需要 cookie，而 cookie 可以用任何方式获取（包括手工从 DevTools 复制）。

---

## 9. 凭证不能跨机器复制

| 素材 | 为什么不能跨机 |
|---|---|
| `DY_COOKIES` | 绑定 `ttwid` / `odin_tt` 设备指纹 |
| `DY_PRIVATE_KEY` | 浏览器在本机生成的 P-256 密钥 |
| `DY_TICKET` / `DY_TS_SIGN` | 签发给那把本机私钥 |
| `DY_DTRAIT_BLOB` | 设备特征指纹 |

**换机器必须重新登录、重新提取。**
