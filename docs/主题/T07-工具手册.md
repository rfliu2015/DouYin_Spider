## 1. 项目自带的采集入口

### 1.1 `main.py`

```bash
python main.py
```

| 段 | 功能 | 风险 |
|---|---|---|
| 1 | 作品详情 | ✅ 安全 |
| 2 | 用户全部作品 | ✅ 安全 |
| 3 | 搜索 | ✅ 安全 |
| 4 | **私信** | ⚠️ **会真的发消息，别误触** |

**依赖**：`.env` 里有 `DY_COOKIES`。

### 1.2 `feed_crawler.py`（推荐流采集）

```bash
python feed_crawler.py --one 'https://v.douyin.com/xxxx/'   # 单条指定采集
python feed_crawler.py --stats                              # 看库统计
```

`--one` 接受抖音 App 分享文案整段、短链、完整链接或纯 `aweme_id`。

#### ⚠️ 评论数与作者显示不一致是正常的

作者页显示的评论数 = **一级 + 全部二级**。`comment/list/` 返回的
`reply_comment` 只是**预览**（通常 ≤3 条），真实回复要另打
`comment/list/reply/`。

| 口径 | 首抓（无补抓） | 补抓后 |
|---|---|---|
| 一级评论 | 102 | 103 |
| 二级回复 | 7（全是预览残片） | 187 |
| 合计 | **109** | **290** |
| 作者显示 | 286 | 290 |

**实测（2026-10-30，`aweme_id=7702242500257287475`）**：

- 30 条一级评论带回复，`reply_comment_total` 求和 182，全部抓到
- `get_work_all_inner_comment` 单条就能拿全（某条 total=59 → 返回 59 条）
- **翻页会重叠**：某条 total=13 抓到 13 条里有 2 条重复（唯一 11 条）
  → 必须按 `cid` 去重，否则存储层 `INSERT OR IGNORE` 静默吞掉，
  条数比 JSON 少、对不上

`feed_crawler._fill_replies()` 因此做了三件事：逐条抓（不用
`get_work_all_comment`，它无节流无容错，单条失败整批中断）、按 cid 去重、
失败保留预览不清空。

#### ⚠️ 限频/风控：一级评论和二级回复都要控速

**根因**：上游 `dy_apis` 的两个翻页函数 `count` 都硬编码、且**循环里完全没有
sleep**——`get_work_all_out_comment()` 是 5，`get_work_all_inner_comment()`
也是 5。翻页次数被放大 10 倍，额度就是这样被一次采集烧光的。

> **2026-10-31 修正：此前把主因归到一级评论侧（"比回复侧有节流，密集得多"）
> 是错的。** 真正的重灾区是**回复侧**：一级评论一条作品最多 1000 条、按
> count=5 也就约 200 次请求；而回复侧单条评论就能有上千条回复——实测一条
> 1230 条回复的评论，按 count=5 要**连打 246 次请求、耗时 74 秒**，
> 单条评论就把整个 IP 的回复额度耗尽。
> 这解释了"1/35 条评论成功"的真相：**不是第 1 条就触发限频，而是第 1 条
> 就用完了额度**。

采集器因此两边都不复用上游，各有一套自己的翻页：

| 参数 | 值 | 说明 |
|---|---|---|
| `COMMENT_PAGE_SIZE` | `'50'` | 一级评论每页条数，服务端上限 |
| `COMMENT_THROTTLE` | `1.0` 秒 | 每次翻页的固定间隔 |
| `COMMENT_LIMIT` | `1000` | 够量即停，省下的请求都是风控额度 |
| `REPLY_PAGE_SIZE` | `'50'` | 二级回复每页条数，服务端上限 |
| `REPLY_PAGE_THROTTLE` | `1.0` 秒 | 回复翻页间隔 |
| `REPLY_LIMIT` | `400` | 单条评论的回复数**软上限**，见下 |

**`count` 服务端上限 = 50（实测）**：

| 接口 | `count=20` | `count=50` | `count=100` |
|---|---|---|---|
| 一级评论 `comment/list/` | 返回 17 条 | **返回 47 条** | 返回 47 条 |
| 二级回复 `comment/list/reply/` | 返回 20 条 | **返回 50 条** | 返回 50 条 |

传 100 不报错，但**仍只给 50 条**——50 是硬上限，再往上加没有意义。
`cursor` 会同步推进到请求值，确认是真分页。

**效率对比**（同一条 711 条回复的评论）：

| 配置 | 请求次数 | 耗时 |
|---|---|---|
| 原 `count=5`（无 sleep） | 143 次 | ~74 秒 |
| `count=20` + 1s 节流 | 36 次 | 13.8 秒 |
| **`count=50` + 1s 节流** | **4 次** | **5.8 秒** |

整条作品的一级评论从 56 页降到 22 页，全程从 3 分 22 秒降到 1 分 22 秒。

`dy_apis` 只新增了可选参数 `count`，**默认值仍是 5 / 3**，`main.py` 等入口
行为不变——节奏控制留在采集器里，不动通用层默认值，避免第三方脚本请求量
突然涨 10 倍。

**`REPLY_LIMIT` 是软上限**：`_fetch_all_inner_comments()` 先整页追加、再判
是否够量，而服务端每页常少于请求值（请求 50 只回 47），所以实际会**超出一页**。
实测 `REPLY_LIMIT=400` 时，单条评论抓到 445 条（400 + 末页）。需要严格上限
就在返回处加切片。

#### 回复筛选：不是所有评论都值得抓

风控的根源是**请求次数**，不是数据量。一条 226 条带回复评论的作品要发 226 次请求，
必须筛选。`_select_reply_targets()` 做两级筛选：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `REPLY_TOP_PCT` | `0.45` | 按 `digg_count` 降序取前 45%（至少保 1 条，防全滤光） |
| `REPLY_BUDGET` | `35` | 单条作品的回复请求数**硬上限**，0=不限 |

流程：先按点赞取前 45% → 再按预算截断。日志会打印决策：

```
补抓二级回复：带回复 224 条，按点赞取前 45% → 101 条，预算截断 → 35 条（实际请求 35 次）
```

> **预算取 35 的理由，以及它的局限**：
> 实测同一 IP 上连续回复请求的触发点**不是固定值，而是随累计消耗持续下降**——
> 100 预算时第 42 次触发，改用 35 预算后**第 16 次就触发**。
> 所以预算只是"少扣一点"，**并不能保证避开风控**（见下方实测边界）。
> 取 35 是因为它对正常作品够用、又比 100 少发一半请求；不要把它当成解决方案。

**为什么选点赞数**（2026-10-31，4574 条带回复评论的实测）：

| 策略 | 保留请求 | 削减 |
|---|---|---|
| `digg_count >= 10` | 29% | 71% |
| `reply_comment_total >= 5` | 25% | 75% |
| **按点赞取前 45%** | ~45% | ~55% |
| `is_hot=True` | **95%** | ❌ 等于没筛 |

- **点赞前 30% 的评论覆盖 69% 的回复量，前 50% 覆盖 81%** —— 少数高赞评论下才有讨论
- `is_hot` 占 95%，**不能用它筛**

`top_pct=1.0` + `budget=0` 可回到"抓全部"的旧行为。

**命令行覆盖**（也可用 `.env` 的 `REPLY_TOP_PCT` / `REPLY_BUDGET`）：

```bash
python feed_crawler.py --one <链接> --reply-top-pct 0.3 --reply-budget 50
python feed_crawler.py --one <链接> --reply-top-pct 1.0   # 抓全部
```

> ⚠️ **筛选对小作品无意义**：某作品一级评论 201 条、带回复只有 12 条，
> 按 45% 取前是 5 条，几乎全中。限制小作品的是**预算**，不是比例。

#### 二级回复的延迟策略：正常随机 + 失败指数回退

`_reply_delay(streak)` 一个函数管两种情形：

| 情形 | 延迟 | 参数 |
|---|---|---|
| 正常 | **0.5~2 秒随机** | `REPLY_DELAY_MIN` / `REPLY_DELAY_MAX` |
| 连续失败 | **2 → 4 → 8 → 16 秒**，封顶 60 | `REPLY_BACKOFF_BASE` / `REPLY_BACKOFF_MAX` |
| 第 5 次连续失败 | **中止**，放弃剩余回复 | `REPLY_ABORT_AFTER=5` |

设计要点：

- **正常态用随机而非固定间隔**：固定节奏太规律，0.5~2 秒抖动更像真人，
  也避免每次请求都踩在同一时间窗
- **回退态不叠加随机**：此时要的是明确变慢，随机反而让等待时长不可预期
- **一旦成功 `streak` 归零，立刻回到 0.5~2 秒随机**，日志会打
  `已恢复（此前连续失败 N 次）`
- **阈值须大于回退能生效的次数**。取 5 意味着有 4 次回退（2+4+8+16=30 秒）
  的试探余地；若设成 3，回退还没长起来就中止了

**翻页会重叠，必须去重**：一级评论和二级回复都一样。

- 实测某作品一级取 1000 条，**唯一只有 783 条**（重复 217）
- 某条 `total=13` 的评论，抓 13 条里 2 条重复（唯一 11）

`_dedup_by_cid()` 按 `cid` 去重。⚠️ **必须先去重再截断**——顺序反了重复项会白占
`COMMENT_LIMIT` 名额，实际唯一数远小于上限。

> 存储层 `UNIQUE(aweme_id, comment_id)` + `INSERT OR IGNORE` 会静默吞掉重复，
> 所以**库里看不出来，但 JSON 和日志计数会虚高**。日志里的「评论 N 条」
> 是**新增插入数**，不是抓取数，重抓同一作品时会明显偏小。

**风控有两种，严重程度不同**：

| 类型 | 报错 | 能否靠等待恢复 |
|---|---|---|
| 限频 | `接口返回空响应（HTTP 200）` | ✅ 冷却后可恢复（实测约 2 小时后） |
| **人机验证** | `触发人机验证（bdturing slide）` | ❌ **等多久都没用**，需在浏览器手动过滑块或换 IP/账号 |

限频阶段用回退试探；**一旦出现 `bdturing slide`，继续重试只会加重账号风险等级**。

应对流程：

- 先指数回退试探（2→4→8→16 秒），成功即恢复
- 连续 5 次仍失败 → 判定已被限频，**放弃剩余回复、保留已抓部分、照常落盘**
- 修改前的行为是失败也继续逐条打点，实测硬打 116 次全失败才结束，
  既拿不到数据又加重封禁风险

**实测边界（2026-10-31，`aweme_id=7696125570802923365`，约 4900 条评论）**：

| 轮次 | 一级评论 | 回复 | 请求数 | 结果 |
|---|---|---|---|---|
| 改前 | 1000（唯一 783） | 1241 | 217 | 硬打 116 次后中断 |
| 改后第 1 轮 | 1018（唯一 807） | 697 | 217 | 53 条评论后中止 |
| 改后第 2 轮 | 812（零重复） | 730 | 217 | 55 条，**报错升级为 `bdturing slide`** |
| 改后第 3 轮（+筛选） | 828（零重复） | 943 | **100** | 43 条后中止，累计 2240 条（46%） |
| 换新账号后 | 1018（零重复） | 701 | **100** | **42 条**后中止 |
| 预算降到 35（冷却 43 分钟后） | — | 0 | **35** | **16 条**后中止 |

**⚠️ 三次初判都被实测推翻，别照抄结论：**

**其一，不是"账号风险累积"**。换全新账号（`sessionid` `f32f0a80…` →
`3aeddcdc…`，ticket 同步更新，公钥验证通过，探测时接口完全正常），
照样在第 42 次被限频，与旧账号的 43 次几乎相同 → **限制在 IP 层**。

**其二，IP 阈值也不是固定 42**。把预算压到 35、并等 43 分钟冷却后重测，
**第 16 次就触发了 `bdturing slide`**。同一时间点上，前后三次单发请求
（一级评论 / 作品详情 / 另一作品评论）却全部成功。

**其三（2026-10-31 晚补测，最重要）："第 N 条评论就中止"这个计数口径会
严重误导，应改按「请求次数」计。** 两台机器跑同一作品
（`aweme_id=7683162604865885355`），日志分别显示"1/35"和"2/35 条评论成功"，
看起来像触发点从第 16 次暴跌到第 1 次。**但真相是**：

- 当时的回复翻页是 `count=5` 且**循环内零 sleep**，一条 1230 条回复的评论
  要连打 **246 次请求（74 秒）**
- 所以"1/35"不是"第 1 条就触发"，而是**第 1 条就把整个 IP 的额度烧光了**
- 两台机器"1 条 vs 2 条"的差异，只是前两条评论的回复量大小不同而已；
  按请求次数算，两边的触发点**高度一致**

这同时也说明：**改 `count` 比调 `REPLY_BUDGET` 有效得多**——调预算只是
少发几个请求，改 count 是把单个请求的信息量提高 10 倍。

所以真实机制更像：**该 IP 的评论请求额度被持续消耗，触发点随累计量下降，
且是间歇性的**（单发能过、连发就挂）。**降低单次预算只能少扣一点，
不能保证避开。** 真的要稳定采集，只有换 IP。

> 这意味着 `REPLY_BUDGET=35` 的定位是"少发请求、减小影响面"，
> **不是风控的解决方案**。要更多数据必须接 proxies（`dy_apis` 支持，
> `feed_crawler` 尚未接入）。

> **`bdturing slide` 的表现是间歇的**：同一分钟内可能一会儿通、一会儿挂。
> 遇到报错先探测一次再决定，不要直接判定需要手动过验证。

**修复后实测（2026-10-31 晚，`aweme_id=7683162604865885355`，
约 4.2 万条评论 / 1000+ 一级评论）**：

| 阶段 | 回复翻页配置 | 单条评论上限 | 补抓结果 | 二级回复累计 |
|---|---|---|---|---|
| 修复前 | `count=5`，无 sleep | 200（硬） | **1/35 中止** | **2 条** |
| 改 count=20 | `count=20` + 1s 节流 | 200（软） | **35/35 全成功** | 1536 条 |
| 改 count=50 | `count=50` + 1s 节流 | 200（软） | 35/35 | 1727 条 |
| 放开上限 | `count=50` + 1s 节流 | **400（软）** | 35/35 | **2359 条** |

**关键结论：同一 IP、同一账号，只把 `count` 从 5 改成 20，补抓成功率就从
1/35 变成 35/35。** 全程再没触发限频。说明此前"该 IP 额度已耗尽"的判断
过于悲观——额度是被 `count=5` 的翻页浪费掉的，不是天然不够。

| 整条作品 | `count=20` | `count=50` |
|---|---|---|
| 一级评论页数 | 56 页 | **22 页** |
| 全程耗时 | 3 分 22 秒 | **1 分 22 秒** |

**结论：该作品无法靠单次采集拿全。** 5 轮累计约 2400/4900 ≈ 49%。
**要更多数据必须换 IP**（`dy_apis` 支持 proxies 参数，但 `feed_crawler` 尚未接入），
换账号无效。

即使没有风控，该作品 224 条带回复评论也需要 224 次请求，远超
`COMMENT_LIMIT=1000` 能覆盖的一级评论量——**评论量数千的作品无法一次采全**，
需要断点续抓（当前未实现，每次重跑都从头开始、重复请求已成功的部分）。

> 限频判据：出现 `error_code=7` 立即停，不要重试（见 [当前状态](../状态/S01-当前状态.md) §4）。

#### 增删主题 / 调整阈值

主题有两处来源，**后者覆盖前者**：

| 来源 | 位置 | 是否入库 |
|---|---|---|
| 默认 | `utils/topic_classifier.py` 的 `DEFAULT_THEMES` | ✅ 提交 |
| 覆盖 | `datas/feed/themes.json` | ❌ `datas` 已 gitignore |

`feed_crawler.py` 启动时检查 `datas/feed/themes.json`，存在就整份替换默认主题
（不是合并），并打印 `使用自定义主题文件`。

**改代码里的（推荐，可复现）**

编辑 `DEFAULT_THEMES`，一个主题三个键：

```python
{
    "name": "成长",
    "desc": "个人成长、自我提升、励志与奋斗、心态建设、习惯养成、"
            "自律与坚持、目标管理、行动力、突破舒适区。",
    "neg":  "纯历史事件叙述不算；具体的社交规则与处世技巧归「为人处世」，"
            "不在此列；心理机制与理论分析归「心理学」，不在此列。",
}
```

- `desc` 决定**召回**：写具体场景，别写抽象大词
- `neg` 决定**准确率**：`topic_classifier.py` 顶部注释记过，模型正是靠
  「作者名含 AI 但内容无关的不算」排掉游戏作者才变准的
- ⚠️ **加主题必须同步改相邻主题的 `neg`**。若「成长」把励志类内容收走，
  就要把「为人处世」「心理学」里"励志鸡汤不算"改成"归「成长」，不在此列"；
  否则模型会同时读到"励志不算"和"励志算成长"，判定漂移

**改 json 的（临时试，不入库）**

```powershell

python -c "import json,sys;sys.path.insert(0,'.');from utils.topic_classifier import DEFAULT_THEMES as d;json.dump(d,open('datas/feed/themes.json','w',encoding='utf-8'),ensure_ascii=False,indent=2)"
```

**验证一次判定**（不必等定时任务）

```powershell

# 看输出里的「命中: 成长(0.65)」这行
```

阈值：`--threshold 0.9` 单次覆盖，或 `.env` 里 `TOPIC_THRESHOLD` 长期生效，

## 2. `browser_credential.py`（fork 新增）

从浏览器 leveldb 提取 `bd-ticket-guard` 素材并写入 `.env`。

### 2.1 三种用法

```powershell
# 列出找到的 profile
python browser_credential.py --list

# 试提取，不写盘
python browser_credential.py --profile "<profile 目录>" --dry-run

# 正式写入 .env
python browser_credential.py --profile "<profile 目录>"
```

### 2.2 ⚠️ 必须显式指定 `--profile`

**不带 `--profile` 会按 mtime 自动选 profile，大概率选错**（会挑到便携版 Chrome，其主密钥解不开）。

**各浏览器 profile 路径**：

| 浏览器 | 路径 |
|---|---|
| 360 极速（推荐） | `D:\Software\0-9\360ExtremeBrowser\360ChromeX\Chrome\User Data\Default` |
| Edge | `%LOCALAPPDATA%\Microsoft\Edge\User Data\Default` |
| Chrome | `%LOCALAPPDATA%\Google\Chrome\User Data\Default` |

> 浏览器是否可用，见 [凭证提取](T03-凭证提取.md) §3。

### 2.3 前提：完全退出浏览器

Cookies 库被独占时返回 `err=32`。

```powershell
# 检查 360
Get-Process -ErrorAction SilentlyContinue | Where-Object { $_.ProcessName -match '360' } | Measure-Object

# 检查 Edge
Get-Process msedge -ErrorAction SilentlyContinue | Measure-Object
```

> **注意**：Edge 关闭窗口后仍有后台驻留（`--no-startup-window`），需要 `Stop-Process`。
> **但不要为了做实验反复强杀浏览器进程**——这曾导致 Cookies 库被清空。

### 2.4 成功输出

```
素材 4 项, cookie 63 个
  私钥        1f25c2ff830312d584ea5cd93cc7c978...
  推导公钥    BNm1FR3DmlH99Zc41+Waa6rmsdscBLvYPYalOi6qAct8bz51...
  公钥验证    通过          ← 必须通过
  ticket      hash.5xW9F7+MU4YeSpnGspicP5/Ek9aJlFZISMQkCfzWvqE...
  ts_sign     ts.2.645de8014ed9cd7d9cb656a71675866620d33d76b0c...
  client_cert pub.BNm1FR3DmlH99Zc41+Waa6rmsdscBLvYPYalOi6qAct8...
  cookie      63 个
    sessionid                有
    UIFID                    有
    ttwid                    有
```

**判据**：

| 项 | 要求 |
|---|---|
| 素材 | 4 项齐全（私钥 / ticket / ts_sign / client_cert） |
| 公钥验证 | **通过** |
| cookie | 60+ |
| sessionid / UIFID / ttwid | 全部「有」 |

任一不满足 → 不要写入 `.env`。

### 2.5 失败模式

| 报错 | 原因 | 处理 |
|---|---|---|
| `DPAPI 解密失败` | 主密钥是非标准格式 | 换浏览器（便携 Chrome 会这样） |
| `AppBoundEncryption` | 浏览器启用 App-Bound（v20） | **换浏览器**（Edge 156 会这样） |
| `Cookies 被浏览器独占（err=32）` | 浏览器没完全退出 | 退出浏览器 |
| `没有提取到任何素材` | 该 profile 未登录抖音 / 未触发 ticket | 重新登录并点赞再取消 |

```bash
DY_PRIVATE_KEY='b64:LS0tLS1CRUdJTi...'   # PEM 压成单行 base64
DY_COOKIES='UIFID_TEMP=...; ...'
```

### 3.3 身份判据（`profile/self`）

> ⚠️ **不能用裸 cookie 请求**，那样永远返回「用户未登录」，是假阴性。

```python
import dy_apis.douyin_api
from utils.common_util import load_env
from builder.header import HeaderBuilder, HeaderType
from builder.params import Params
import utils.http_client as rq

a = load_env()
headers = HeaderBuilder.build(HeaderType.GET)
headers.with_bd_readonly(a)
headers.with_csrf(a.cookie_str)
headers.with_uifid(a)
headers.set_header('referer', 'https://www.douyin.com/')

p = Params()
p.with_platform(round_trip_time='0')
p.with_web_id(a, 'https://www.douyin.com/')
p.with_uifid(a)
p.with_verify_fp(a)
p.add_param('msToken', a.msToken)
p.with_a_bogus()

r = rq.get('https://www.douyin.com/aweme/v1/web/user/profile/self/',
           params=p.get(), headers=headers.get(), cookies=a.cookie, verify=False)
j = r.json()
print(j.get('status_code'), j.get('status_msg'), (j.get('user') or {}).get('nickname'))
```

**判据表**：

| 返回 | 含义 | 下一步 |
|---|---|---|
| `status_code: 0` + `user` 有内容 | ✅ 环境正常 | 可继续 |
| `status_code: 0` + `status_msg: blocked` | ❌ 环境/账号被标记 | 换环境或换账号 |
| `status_code: 8 用户未登录` | ❌ cookie 或 ticket 失效 | 重新登录提取 |
| HTTP 403 `ArgusSecurityPlugin` | ❌ 缺 secsdk 签名 | 走 `sign_url()` |
